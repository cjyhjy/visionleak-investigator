# ADR-014: Single-pass finalization and an explicit accounting commit

`reports/finalization-accounting-gap-v1` reproduced a real accounting omission: the full HTML renderer ran twice, but the second render/write happened after settlement. A controlled 0.3-second delay in that second render was absent from the ledger. Revision proposal/evidence assembly also ran outside its finalization reservation.

Ordinary audits, host revisions and conservative recovery now share `publication.publish_report`. Revision finalization is reserved immediately after the charged metadata interpretation, before review/proposal/evidence assembly. The measured interval includes that assembly, one full HTML render, serialization of the non-accounting JSON body, staged content writes and fsync, and hashing the staged HTML. There is no second full render or full report rewrite. Render and staged-write delays are measured independently in acceptance and must fit within the recorded finalization interval.

The final duration cannot include recursively recording its own last value. The accounting commit therefore has an explicit boundary: settle/persist the ledger, append the measured budget/state/publication metadata to the already-written JSON body, publish the staged files exclusively, then save the final checkpoint. These accounting writes are included in the evaluator's whole-worker wall/CPU/RSS receipts, and are not described as part of the self-recorded tool interval. This remains cooperative tool budgeting, not an OS hard wall-time or I/O sandbox. The distinction is recorded in every new report's `publication` object rather than hidden in a performance claim.

The static HTML is deliberately a labelled pre-settlement budget snapshot. It links to `ledger.json` and the final `report.json` for the final budget/time values; pending in that HTML describes its snapshot time, not a live task. The final JSON report embeds the settled ledger as before. This avoids silently showing stale numbers as final and avoids recursively rendering the whole page to display its own rendering cost.

If the measured operation exceeds its reservation, the ledger preserves the actual overrun and the JSON state becomes PARTIAL. The original page is preserved as `report.before-overrun.html`; the accepted `report.html` is a small status receipt linking to the final records, without a second evidence render. The accepted HTML hash, finalization call and measured duration are bound to the report/checkpoint.

Before acceptance, JSON/HTML use pending names. Exclusive hard-link publication prevents replacement of an existing report. Rendering/publication errors retain raw outputs and write a failure receipt; a pending reservation is conservatively charged. Recovery can quarantine a partially published report only if no accepted report digest exists in its checkpoint. A tampered previously accepted report is rejected, not silently recovered. Recovery does not rerun Core or resurrect unaccepted claims.

The acceptance uses actual Core and the real renderer with explicitly controlled latency/failures, plus ordinary report/revision/recovery regressions. It does not establish natural-data performance, live Agent behavior, or human time savings.
