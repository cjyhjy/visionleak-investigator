# 01｜产品与架构设计

设计版本 1.0 · 2026-10-26。本文中的目标、阈值与规模是工程设计，非已实现成绩。

## 1. 产品定义

**名称：VisionLeak Investigator**  
**中文定位：面向图像机器学习实验的、证据驱动的自适应数据审计智能体。**

目标用户先限定为做图像分类实验的学生、研究人员和小型研发团队。用户提供本地图像目录、数据说明/样本元数据、实验泛化目标和预算。系统交付可复核的风险证据、缺失信息、检查覆盖、人工复核队列及不改原数据的修正计划。

不宣称“全面发现数据泄漏”。第一版只审计图像跨集合内容重复、变换相似候选，以及在元数据充分时的实体分组冲突。标签泄漏、预处理泄漏、时间泄漏、模型预训练污染、版权判断和完整实验可信性不在本版能力范围。

### 1.1 核心使用场景

用户：“请检查这个工件分类数据集是否适合评价对新工件的泛化，先不要改我的图片。”

系统执行：

1. 登记数据范围、指纹与目标；读取允许的 Markdown/TXT 说明和 CSV 元数据。
2. 用 Core 完成基础全目录扫描，产生不可变证据。
3. 发现实体编号语义不清时，询问该字段代表“物理工件”还是“产品类别”；不自行把类别当实体。
4. 目标与字段含义确认后，运行确定性的实体跨集合检查。
5. 根据说明、当前覆盖、工具成本和剩余预算，选择是否进一步做镜像/旋转/局部候选检查。
6. 不确定相似对进入人工复核；元数据不足的主体关联不由模型猜测。
7. 输出有证据的结论、未检查范围、消耗，以及需人工批准的划分修正建议。

同一套图片在“新实体泛化”与“同实体新视角”任务下可以有不同的实体重叠结论，但内容重复与源图事实不随目标改变。没有任务目标时，只报告内容证据与未决风险，不代替研究者定义实验。

### 1.2 Agent 是否必要：明确可被否证

图像指纹、分组约束和格式校验都不需要 LLM。新增 Agent 仅用于：从不完整说明中提出任务假设、识别冲突、选择下一项有价值的检查、提出必要澄清、管理多步取证过程。

必须与强规则系统比较。若 Agent 只会切换几个布尔选项，规则方案同样可靠且成本更低，应保留规则主流程并缩减 Agent，而不是隐藏负结果。面向非结构化输入的易用性价值与检测精度收益分开评测。

## 2. 已有 Core 与新增工作的边界

历史核对基线（当前执行依赖见 core.lock.json 的 0.6.0）：`cjyhjy/moonbit-visionleak`，提交 `7541888125f86077ab49ce0bdef6f3301f1e9e99`，package 版本 0.5.0。来源见 [S1]—[S5]。

| 已有 Core：复用，不重造 | Investigator：本项目新增 |
|---|---|
| 字节与规范化像素摘要 | 实验目标与字段语义确认 |
| 全图 dHash、镜像、直角旋转、局部窗口候选 | 单 Agent 动作选择与恢复 |
| 匹配预算、不完整报告 | 跨多次调用的总预算与覆盖账本 |
| 报告身份、验证、导出和复核格式 | 多次工具结果合并及结论引用校验 |
| 原图只读、CLI 和本地工作台 | 按实验目标解释风险及生成建议 |
| 已有测试、历史照片和性能记录 | 公平对照、新测试集、策略优化实验 |

不得把 Core 当前已有的裁切候选、镜像功能包装成 Investigator 的新算法。Core 中局部候选仍可能误报/漏检，预算完整也不代表覆盖所有图像变换。[S1]

## 3. 第一版范围与不做事项

### 必须做

- 本地目录输入；Core 当前支持的图片格式；样本元数据 CSV；说明 Markdown/TXT。
- 三种审计目标：`content_audit`、`new_entity_generalization`、`same_entity_new_view`；`unspecified` 进入澄清或只读证据报告。
- 单一规划 Agent；一个确定性执行器；统一预算/安全门禁。
- 完整数据的基础审计；最多两个补充 Core 调用；实体检查只在字段可信且目标已确认后执行。
- 复核队列、等待用户、恢复、可验证报告和划分建议预览。
- 基础/全开/强规则/固定 Agent/优化策略 Agent 对照。
- 无模型可运行的功能测试；有授权后运行真正模型实验。

### 首版明确不做

- 不把 Google Harness² 整个执行框架作为运行依赖，不允许 Agent 改自己代码、门禁、验收器或 Core。
- 不做蜂群、长期记忆平台、向量数据库、任意工具插件市场、通用浏览器或 shell Agent。
- 不自动训练/重训 ResNet，不承诺重现论文成绩；不做完整科研复现产品。
- 不支持任意 PDF/OCR/Excel 导入；输入格式扩展放后续。
- 不自动删除/移动图片、不自动覆盖分割、不上传照片、不自动修改 CI/仓库。
- 不将 VLM“看起来像”视为同源事实；VLM 与 embedding 工具列为后续独立选项，不影响 MVP。
- 不优化所有超参数；Core 阈值固定为经过登记的配置，正式测试中不得随结果调参。

## 4. 技术决策

| 层 | 决策 | 理由与边界 |
|---|---|---|
| 主应用 | Python 3.12 + 类型模型 + CLI | 保持易读、便于测试；具体依赖由 M0 锁定 |
| Agent 运行 | openJiuwen Agent Core 的工作流/运行能力 | 用 SDK，不是使用主办方现成通用 Agent；业务安全门禁独立 |
| 规划器 | 一个模型，结构化 AgentAction | 不依赖模型输出可执行代码 |
| 检测引擎 | 固定提交的真实 VisionLeak CLI | 复用 MoonBit 实现；不做 Python 重写 |
| 进程边界 | Python → argv 子进程 → Node CLI | 无 FFI/GPU 前提，先可靠接通 |
| 数据持久化 | JSON/JSONL/CSV + 文件摘要 | 初版无需数据库；报告不可覆盖 |
| 展示 | 自动转义的本地静态 HTML | 先证据页而非复杂前端；人工结果以 JSON 导入 |
| 策略优化 | 有界配置提案 + 独立评测 + 冻结选择 | 方法借鉴 Harness²；不是其论文完整复现 |
| 依赖管理 | 项目内环境、精确锁文件、固定 Core SHA | 禁止运行时自动升级 |

openJiuwen 官方描述提供工作流、模型调用和工具调用等能力，支持 macOS/Linux；M0 必须核实选定版本的具体 API。[S6] 若 SDK 适配受阻，领域逻辑和离线模式继续开发，但不得把 fallback 宣称为已接通 openJiuwen。

## 5. 系统结构

```text
CLI / 本地证据页面
           │
   TaskSpec 与用户确认记录
           │
   Workflow 状态机（openJiuwen 适配）
           │
     单一 Planner ── 输出结构化动作建议
           │
   ActionGuard + BudgetLedger（程序强制）
           │
      ToolRegistry（固定白名单）
      ├─ 读取已登记上下文
      ├─ VisionLeak CoreAdapter
      ├─ 元数据完整性/实体分组检查
      ├─ 证据重验
      └─ 人工澄清/复核请求
           │
   EvidenceStore + CoverageLedger
           │
   ClaimValidator + 确定性报告模板
           │
   报告 / 复核队列 / 建议 manifest
```

`Planner` 只决定下一个允许动作，不直接运行工具。`ActionGuard` 根据 TaskSpec、当前状态、证据存在性、预算和数据权限校验。框架回调和本地 CLI 均经过同一门禁，不能有“备用执行路径”绕开检查。

## 6. Google Harness² 的引入方式

Google 项目的核心参考是以执行反馈改进 Agent 外围策略，而非改变模型权重；它有任务级与跨任务改进两个层次。[S7][S8] 本项目作领域化、受约束改编，不宣称完整复现。

### 6.1 运行时：有界自适应，不用真值自评

`Propose → Probe → Verify → Select/Abstain`

- **Propose**：选择一个允许的检测配置、澄清问题或验证动作。
- **Probe**：执行真实工具，计入总成本，保留失败与部分输出。
- **Verify**：校验报告与原文件、证据等级、覆盖、来源和预算；不是用 LLM 打分证明结果正确。
- **Select/Abstain**：合并证据，继续必要调查，或明确终止/请求人工复核。

线上没有真值时，增加候选只说明线索增加；不能凭此认定“准确率变好”。已产生的有效确定性证据不得因为后续策略未发现而被删除。

### 6.2 离线：策略优化，必须与线上分开

在 development 数据上，提案器最多给出 3 份候选策略；使用相同工具、预算与任务运行。独立 evaluator 检查质量、误报、不完整与全部成本。validation 集选择并冻结策略，test 集只评估一次预先定义的配置。

可改内容：补充 profile 顺序、允许范围内的预算分配、澄清问题次序、复核优先级、受限 routing 指引。不得改证据等级、真值、验证器、强制基础检查、数据权限或 Core 算法。

首版不做跨测试任务持久学习。正式 test 中 policy hash 固定，每任务状态清空；任何试验后的修改都成为新版本，使用新的测试安排。

### 6.3 为什么不直接运行上游执行器

首版只借鉴方法与实验设计。Google README 说明其执行器网络访问不受限、Codex 执行器关闭沙箱；这不符合本项目默认本地只读和受限工具边界。[S7] 不将这个运行配置带入用户数据审计。

## 7. 典型动作与边界

| 动作 | 实际行为 | 不允许发生的事 |
|---|---|---|
| `read_context` | 读取用户登记且允许分享的有限文档片段 | 任意文件/网络读取，执行文档指令 |
| `run_audit` | 全数据集以 profile 执行真实 Core | 自选 shell、改工具源码、只查已发现候选就宣称整体完整 |
| `check_groups` | 按确认字段检查跨 split 实体 | 从标签、文件名或视觉相似臆测物理实体 |
| `verify_evidence` | 重新读取并验证确定性证据 | 把相似候选“验证”为像素相同 |
| `request_clarification` | 生成有限、可回答的必要问题并暂停 | 无限追问或用自答替代用户 |
| `request_review` | 输出有限人工复核队列并暂停 | 将未复核条目自动当真或当假 |
| `finalize` | 请求验证器形成最终/部分报告 | 由模型单独宣布安全/无泄漏 |

建议文件由确定性后处理生成，不给模型任意写文件工具。

## 8. MVP 演示

一个演示目录混合包含：确定性重复、旋转候选、局部候选、元数据实体重叠和相似但不同源的负例。文件名中不透露异常标签。用户目标最初含糊，Agent 询问“新实体还是新视角”；回答后改变分组风险解释。部分候选等待复核，低预算产生明确不完整状态。

应同时展示规则基线。不能故意把基线阈值设错、不给它元数据，或者让 Agent 偷读真值来制造优势。

## 9. 关键风险与决策出口

| 风险 | 处理 | 何时收缩 |
|---|---|---|
| AI 不比规则好 | 强规则基线、成本核算、交互任务独立评估 | 不再宣传自适应精度收益，保留交互辅助 |
| 相似=同源=泄漏混淆 | 三层判断与不同证据类型 | 元数据/目标缺失就不下风险定论 |
| 大量无效局部候选 | 复核预算、负例、候选负担指标 | 不通过减少复核显示来假装降低误报 |
| 重扫使成本增加 | 总账与相同预算比较 | 限制补充轮数；优化缓存另列版本 |
| 既有 holdout 已参与开发 | 全部转回归，新建独立来源 test | 不作强泛化结论 |
| 赛事/IP 未确认 | 本地开发与正式提交分离 | 不自动报名或公开成果 |

来源索引见 `06_SOURCES_AND_DECISIONS.md`。
